
1. Hide join URL after copying

User Story — Admin
As an Admin, I want the player join URL to disappear after I click the copy button, so that sensitive join links are not left visible on screen after I’ve copied them.

Technical Story
On the Players page, keep the generated join link visible only until the Admin presses COPY. After a successful clipboard action, replace the visible URL with a state such as “Join link copied” or a masked value. The actual token must not remain rendered in the DOM if possible. Keep the existing copy functionality unchanged. If a new join link is generated, show that newly generated link again until it is copied.

2. Coin icon in Player wallet

User Story — Player
As a Player, I want to see a coin icon next to my wallet balance, so that my balance is visually recognizable as Market Mayhem coins.

Technical Story
Update the mobile wallet/balance component to render a consistent coin icon immediately before the numeric balance. Use the same icon anywhere the primary wallet balance appears. Prefer an inline SVG or existing icon library component rather than an emoji so rendering is consistent across Android, iOS, and desktop.

3. Starting balance animation on first join

User Story — Player
As a Player joining Market Mayhem for the first time, I want to see my coins animate from 0 to my starting balance, so that entering the game feels like receiving my initial bankroll.

Technical Story
Detect the first successful player session/join. On the first mobile landing experience only, render a short wallet onboarding animation that counts the visible balance from 0 to the player's actual starting balance. Do not modify the wallet value during the animation; the real balance must already exist server-side. Store a client/session-level acknowledgement so normal page reloads do not replay it continuously. The animation should work for any configured starting amount.

ROULETTE

4. Visual roulette table

User Story — Player
As a Player, I want to place bets directly onto a visual roulette table, so that roulette feels like an actual casino game instead of filling out a form.

Technical Story
Replace form-style roulette betting with an interactive visual roulette layout. Render numbered cells and supported outside-bet regions. Each valid betting region must be clickable/tappable and map to a canonical server-side bet type/value.

The table should work responsively on mobile and should never rely on screen coordinates as the actual bet definition.

5. Roulette stake placement

User Story — Player
As a Player, I want to choose how many coins I am betting and then place that amount on one or more areas of the roulette table, so that betting feels intuitive.

Technical Story
Add a selected stake/chip amount control above or below the roulette table. Flow:
1. Player selects stake amount.
2. Player taps a valid roulette position.
3. A visible chip appears on that position.
4. Chip displays the amount.
5. Player confirms their bet if confirmation is required.

All final bet validation happens server-side. Do not deduct funds purely from client state.

6. Roulette spinning animation

User Story — Player / Audience
As a Player watching roulette, I want to see the wheel visibly spin before the result is shown, so that resolving the game feels exciting and understandable.

Technical Story
Create a dedicated roulette wheel component for the Big Screen and, where useful, the Admin preview. When Admin triggers a spin, transition the roulette state from something like:

BETTING_OPEN → BETTING_CLOSED → SPINNING → RESULT

Animate the wheel and ball while SPINNING. The animation must resolve to the server-selected winning number; the frontend must never independently determine the financial outcome.

7. Show all roulette bets on Big Screen

User Story — Audience
As someone watching the main screen, I want to see which players have placed bets and how much they have wagered, so that roulette becomes a shared game rather than a private mobile interaction.

Technical Story
When roulette is active, expose a public-safe roulette bet snapshot to the Big Screen containing:
- player display name
- player color
- bet type/position
- stake amount

Render chips/bet markers directly on the visual table where practical. Each visible bet should show the player's name and amount, or use a chip plus a compact nearby label if space becomes crowded. Never expose authentication/session data.

PREDICTIONS

8. Admin sets probability, system calculates odds

User Story — Admin
As an Admin, I want to set a prediction's probability using a visual slider, so that Market Mayhem automatically calculates fixed YES and NO multipliers without requiring me to calculate the odds myself.

Technical Story
On the Prediction create/edit form, add a probability slider from 1% to 99%, default 50%.

As the Admin moves the slider, calculate in real time:

YES multiplier = 1 / probability_yes

NO multiplier = 1 / (1 - probability_yes)

Example:

20% → YES 5.00x / NO 1.25x

Display both multipliers rounded to two decimals.

Persist the canonical probability and multiplier snapshot when the prediction is created/opened.

Recommended database fields:
- probability_yes
- multiplier_yes
- multiplier_no
- status

Do not derive financial settlement later from a potentially changed slider value; each accepted bet should also store the multiplier used at placement.

9. Prediction player view

User Story — Player
As a Player, I want to immediately understand what each side pays, so that I can decide whether the risk is worth taking.

Technical Story
For every active prediction render:

YES @ X.XXx

and

NO @ X.XXx

When the Player enters a stake and selects a side, render:

Potential payout = wager × selected multiplier

Update this immediately as stake or selection changes.

10. Prediction data model/state simplification

User Story — Admin
As an Admin, I want a prediction to have a simple lifecycle, so that I can easily understand whether it is open, settled, or cancelled.

Technical Story
For the prediction-level public status requested here, support at minimum:
- OPEN
- RESOLVED_YES
- RESOLVED_NO
- CANCELLED

If the backend still needs internal scheduling/locking states such as DRAFT, SCHEDULED, or LOCKED, keep those internally, but make sure they map cleanly to the Admin and Player UI.

Do not bring back the old crowd-probability voting system.

11. Prediction-specific timing and stake settings

User Story — Admin
As an Admin, I want to configure the duration and stake limits independently for every prediction, so that high-risk predictions can behave differently from smaller markets.

Technical Story
Remove these from global Settings:
- Prediction time
- Minimum prediction stake
- Maximum prediction stake

Add them to the Prediction create/edit form instead:
- prediction_time_seconds
- minimum_stake
- maximum_stake

Store them on each prediction.

When the prediction opens, calculate closes_at using that prediction's own duration.

Bet validation must use that prediction's own min/max values.

12. Prediction does not automatically take over Big Screen

User Story — Admin
As an Admin, I want predictions to become available on player phones without automatically replacing the main Big Screen, so that I stay in control of what the room is looking at.

Technical Story
Decouple these concepts:
- prediction is open for mobile betting
- prediction is currently featured on Big Screen

When a round starts, predictions may become OPEN for mobile players, but the Big Screen remains on its current content.

Add an explicit Admin action:

SHOW PREDICTION

Only this action changes the Big Screen presentation to that prediction.

13. Show Prediction button

User Story — Admin
As an Admin, I want a SHOW PREDICTION button next to an active prediction, so that I can intentionally present it to the room when the timing is right.

Technical Story
On the Admin Predictions page and/or active prediction controls on the Control Center, add SHOW PREDICTION.

The action updates the Big Screen's active presentation state to reference that prediction.

Do not change prediction betting state when this button is pressed.

14. Mobile prediction card padding

User Story — Player
As a Player, I want prediction cards to have comfortable spacing, so that text and controls do not feel cramped against the edge of the card.

Technical Story
Update the mobile prediction-card styling to add internal padding consistently around:
- title
- status
- multipliers
- bet state
- actions

Check at minimum 320px, 375px, 390px, and 480px viewport widths. Avoid solving it with page-level margin alone; the card itself needs internal padding.

15. Active vs settled prediction styling

User Story — Player
As a Player, I want to instantly distinguish active markets from finished ones, so that I know where I can still bet.

Technical Story
On the Player Markets/Predictions page, create clearly different visual states.

For example:

Active
- stronger contrast
- countdown/status badge
- visible YES/NO controls
- OPEN badge

Settled
- muted card treatment
- result badge
- no active betting controls
- payout/result summary

Do not rely on small status text alone.

16. Make placed bets visually obvious

User Story — Player
As a Player, I want a prediction to clearly tell me when I already placed a bet, so that I do not wonder whether my bet was registered.

Technical Story
Replace or supplement the subtle:

Your bet: X on YES

text with a prominent visual state such as:

✓ BET PLACED

Then show:
- selected side
- deposited amount
- locked multiplier
- potential payout

Disable further betting controls for that prediction.

PREDICTION DEPOSIT MODEL

17. Prediction stake becomes a deposit

User Story — Player
As a Player, I want my prediction wager to act as a deposit while the result is unresolved, so that it is clear the coins are committed but not yet definitively lost.

Technical Story
Introduce a concept of:
- available balance
- locked/deposited balance

When a Player places a prediction bet:
- reduce available_balance
- increase their locked/pending stake
- create the bet and ledger reservation/deposit record
- do not consider the stake permanently lost yet

The UI should communicate that the amount is LOCKED or DEPOSITED.

18. Prediction settlement with deposits

User Story — Player
As a Player, I want my deposit to either be lost or converted into the full multiplier payout once the result is known, so that prediction settlement is understandable.

Technical Story
When prediction settles:

Winning bet
- release/remove the deposit from locked funds
- credit the full return:

stake × multiplier

Example:
- Deposit 20
- Multiplier 4x
- Final wallet credit = 80

Losing bet
- remove the 20 from locked funds
- credit nothing

Cancelled prediction
- return the original 20 to available balance

Ensure the total accounting remains consistent and settlement remains idempotent.

BIG SCREEN / EXCHANGE DASHBOARD

19. Exchange graph starts at starting balance in vertical middle

User Story — Audience
As someone looking at the Market Mayhem exchange graph, I want every player's starting value to begin from the visual middle of the graph, so that gains and losses are equally easy to understand.

Technical Story
The first plotted point for every Player should equal the configured starting balance and be vertically centered in the graph.

The y-axis scaling should dynamically allocate room above and below that baseline. Do not put the starting value at the bottom of the chart.

For example, if starting balance is 100, the visual midpoint represents 100, positive movement rises, negative movement falls.

If later values exceed the initial range, dynamically rescale while keeping the graph readable.

20. Always return to main exchange dashboard

User Story — Admin
As an Admin, I want one obvious button that always returns the Big Screen to the main exchange dashboard, so that I can recover from any question, prediction, or roulette screen instantly.

Technical Story
In the Live Big Screen Preview controls, add a persistent button:

SHOW MAIN DASHBOARD

It should always be available regardless of current Big Screen mode.

Pressing it sets the screen's active presentation mode back to the exchange/dashboard state.

21. Latest prediction results on main dashboard

User Story — Audience
As someone watching the main dashboard, I want to see the latest prediction results alongside the exchange graph, so that I can connect recent market outcomes with changes in player wealth.

Technical Story
Refactor the main exchange dashboard layout so that the graph does not consume the entire content width.

Add a panel to the right of the exchange graph containing recent settled predictions.

Each result should display:
- prediction question
- YES / NO result
- optionally odds
- optionally settlement timestamp/order

Use the latest N results that fit the screen cleanly.

ROUND GROUPS

26. Create groups inside a round

User Story — Admin
As an Admin, I want to create temporary groups inside a specific round and assign players to them, so that team-based rounds can be managed independently from the rest of the game.

Technical Story
Add round-scoped groups.

Suggested schema:

round_groups
- id
- game_night_id
- round_id
- name
- created_at

round_group_members
- group_id
- player_id

Groups belong only to that round.

Admin round editor should support:
- create group
- rename group
- delete group
- add player to group
- remove player from group

Do not make these permanent global teams.

27. Group coin adjustment during active round

User Story — Admin
As an Admin running a team round, I want to award or deduct the same number of coins from every Player in a group at once, so that I do not have to update each Player individually.

Technical Story
When viewing an active round/group, provide:
- signed amount
- mandatory reason
- Save

Example:

+20

applied to a group with four Players creates four separate Player financial adjustments of +20 each.

Use one server-side transaction where practical, and create a separate immutable ledger entry per Player referencing:
- round
- group
- reason

Never create a fake shared wallet unless group wallets are explicitly introduced later.

28. Retroactive group coin adjustments

User Story — Admin
As an Admin, I want to go back to a completed or inactive round and award or deduct coins from one of that round's groups, so that I can correct missed scoring after the round has finished.

Technical Story
Do not restrict group adjustment controls to ACTIVE rounds.

On historical round detail pages, retain group membership and allow an authenticated Admin to apply a signed adjustment.

Each adjustment:
- affects current Player wallet now
- is attributed historically to the selected round/group
- gets current transaction timestamp
- preserves the Admin-entered reason

This should appear properly when filtering Ledger by that historical round.

DUOLINGO-STYLE QUESTION

29. New Duolingo-style round block

User Story — Admin
As an Admin, I want to create a four-option live question inside a round, so that everyone can answer simultaneously from their phones.

Technical Story
Add a new round block type, for example:

MULTIPLE_CHOICE_LIVE

or

DUOLINGO_QUESTION

This is separate from the standard static QUESTION block.

The round content architecture must support its own config/state.

30. Configure Duolingo question

User Story — Admin
As an Admin, I want to define the question, four possible answers, the correct answer, and the coin reward, so that the question can be run without any manual scoring afterward.

Technical Story
In the round content builder, the Duolingo question editor contains:
- question text
- reward coins for correct answer
- answer 1
- answer 2
- answer 3
- answer 4
- correct-answer selector

Associate these four fixed emojis, one per answer:
- 🍆 U+1F346
- 🌽 U+1F33D
- 🍑 U+1F351
- 😳 U+1F633

Persist the answer text and correct-answer index server-side.

The correct answer must not be exposed to Player APIs before the question closes.

31. Big Screen Duolingo question

User Story — Player / Audience
As a Player, I want the main screen to show the actual question and answer choices, so that my phone only needs to act as a controller.

Technical Story
When this block is shown on the Big Screen, render:
- question prominently
- four answer texts
- corresponding emoji next to each answer

For example:

🍆 Amsterdam
🌽 Brussels
🍑 Paris
😳 Berlin

32. Phones automatically switch to answer controls

User Story — Player
As a Player, when a live multiple-choice question appears on the main screen, I want my phone to automatically switch to the four answer buttons, so that I can answer immediately without navigating through menus.

Technical Story
When the Admin activates a DUOLINGO_QUESTION block, increment public/player state.

Player mobile polling detects the active interactive block and switches the primary view into question-answer mode.

The mobile screen should show only the four large emoji answer controls, without repeating the answer text, because the answer text is on the Big Screen.

Buttons:
- 🍆
- 🌽
- 🍑
- 😳

After submission, clearly show a submitted/locked state.

33. One answer per Player

User Story — Player
As a Player, I want my answer to be locked once submitted, so that the question is fair and I know my response was registered.

Technical Story
Create server-side response records, for example:

round_question_answers
- question/block id
- player_id
- selected_answer
- submitted_at

Unique constraint:

question + player

Reject duplicate submissions.

Do not trust client-side disabling alone.

34. Correct-answer reward

User Story — Player
As a Player who answered correctly, I want the configured coin reward to be added automatically, so that scoring is immediate.

Technical Story
When Admin closes/reveals/resolves the Duolingo question:
- compare submitted answer to canonical correct answer
- for each correct Player, credit configured reward
- add immutable ledger entry
- attribute it to the round and question
- update wallet
- increment state version

Wrong/no answers receive no reward unless future configuration says otherwise.

Settlement must be idempotent.

35. Question result state

User Story — Audience
As someone watching, I want the correct answer and outcome to be revealed after everyone has answered, so that the round has a satisfying conclusion.

Technical Story
Support states such as:
- READY
- OPEN
- CLOSED
- REVEALED
- SETTLED

Admin controls opening/closing/reveal where appropriate.

When revealed:
- Big Screen highlights the correct answer.
- Mobile shows correct/incorrect result.
- Rewards settle exactly once.

ROUND BLOCK ARCHITECTURE UPDATE

With these additions, the supported round blocks should now be:
- TEXT
- QUESTION
- DUOLINGO_QUESTION
- ROULETTE

Still explicitly out of scope:
- PowerPoint
- Google Slides
- Google Sheets
- Excel
- generic file presentation

The two biggest architectural changes in this batch are prediction deposits/locked funds and interactive round blocks that can automatically change the Player mobile interface. Those should be implemented as backend state concepts first rather than as purely visual frontend behavior.
