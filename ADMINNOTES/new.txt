## GLOBAL DESIGN REQUIREMENT

**User Story — Admin / Player / Audience**
As a user of Market Mayhem, I want every new feature and every modified screen to follow the same visual language, so that the product remains consistent across Admin, Player Mobile, and Big Screen.

**Technical Story**
All frontend work in this backlog must follow the design rules in:

`ADMINNOTES/designhandboek.txt`

This file is the single source of truth for styling, spacing, typography, colors, cards, controls, layout, animation behavior, responsive rules, and screen hierarchy.

Every story below should be implemented within that design system rather than introducing new standalone styling.

---

## 1. Fix Live Big Screen Preview scaling

**User Story — Admin**
As an Admin, I want the Live Big Screen Preview on the Control Panel to look exactly like the actual Big Screen, only proportionally scaled down, so that I can accurately see what the audience is seeing without oversized components overflowing the preview.

**Technical Story**
The Live Big Screen Preview should render the same Big Screen output as `/screen/:gameId`, not a separately styled approximation.

The preview must:

* preserve the exact 16:9 composition of the Big Screen
* preserve relative font sizes, spacing, graphs, cards, tickers, and overlays
* scale the entire Big Screen composition as one visual unit
* fit completely inside the preview container
* never independently resize individual Big Screen components

A suitable implementation is to render the Big Screen at its canonical design dimensions, e.g. `1920 × 1080`, inside a wrapper and apply a uniform CSS scale/transform based on the available preview width.

Conceptually:

`previewScale = previewContainerWidth / 1920`

The preview container should maintain a `16 / 9` aspect ratio and hide overflow.

Do not create separate breakpoint styles specifically for the preview, because that causes it to visually diverge from the actual projector output.

**Acceptance Criteria**

* If the Big Screen shows a graph occupying 60% of the screen, it occupies the same relative 60% in the preview.
* Text does not appear disproportionately large.
* Nothing is cropped.
* Changing Big Screen content immediately produces the same composition in the preview.

# ADMIN CONTROL PANEL / ROUND FLOW

## 2. Start a round directly from the Control Panel

**User Story — Admin**
As an Admin running the game night, I want to start a round directly from the main Control Panel, so that I do not have to navigate to the Rounds page while hosting.

**Technical Story**
Add a round-control component to `/admin/:gameId`.

When no round is currently active, show:

* next/upcoming rounds
* round title
* round identifier
* `START ROUND` button

Starting the round must use the same backend round-start business logic as the Rounds page.

Do not duplicate start-round logic in a frontend-only implementation.

On successful start:

* mark the round active
* establish its presentation state
* activate any linked prediction logic
* increment relevant public/admin state versions
* immediately show the round-title intro screen on the Big Screen

---

## 3. Round starts with a title slide

**User Story — Audience**
As someone watching the Big Screen, I want every newly started round to begin with a clear title screen, so that everyone understands which round is beginning before the actual content starts.

**User Story — Admin**
As an Admin, I want starting a round to show its title first and wait for me to continue, so that I control the pacing of the event.

**Technical Story**
Treat the round intro as a dedicated presentation step before the first configured round block.

Conceptually, presentation order becomes:

`ROUND_INTRO → BLOCK_1 → BLOCK_2 → BLOCK_3 ...`

The intro does not need to exist as a manually created `round_block`; it can be generated automatically from round metadata.

The title slide should show at minimum:

* round number/identifier
* round title

Optional secondary information may be shown if already supported by the round model.

When `START ROUND` succeeds:

* set `presentation_step = ROUND_INTRO`
* Big Screen renders the title slide
* Admin preview renders the same title slide
* no first content block is shown yet

The system waits until Admin presses `NEXT`.

---

## 4. Next button advances through the round

**User Story — Admin**
As an Admin, I want to press `NEXT` each time I am ready to show the next part of a round, so that I have complete control over the pace of the game.

**Technical Story**
The Control Panel needs prominent round navigation controls whenever a round is active.

At minimum:

* `PREVIOUS`
* `NEXT`

The current position should be visible, for example:

`ROUND 04 · PART 6 OF 8`

`NEXT` should:

* advance from round intro to first block
* then progress through ordered `round_blocks`

`PREVIOUS` should move backward through those same presentation steps.

The backend should maintain canonical current presentation position so:

* Admin refresh does not lose position
* Big Screen remains synchronized
* multiple Admin tabs do not produce divergent state

Do not maintain the active block only in React state.

# BIG SCREEN NAVIGATION MODEL

## 5. Main dashboard is the default Big Screen state

**User Story — Audience**
As someone watching Market Mayhem, I want the exchange dashboard to be the normal resting state of the Big Screen, so that standings and recent market activity are visible whenever no round content is intentionally being presented.

**Technical Story**
The exchange dashboard should be the canonical default Big Screen mode.

Examples of presentation modes might be:

* `DASHBOARD`
* `ROUND_CONTENT`
* `PREDICTION`
* `ROULETTE`

When the game initializes and no other presentation is active, show `DASHBOARD`.

---

## 6. Full round presentation flow

**User Story — Admin**
As an Admin, I want the Big Screen flow for a round to be fully controlled by me, so that I can start the round, introduce it, and reveal each part one at a time.

**Technical Story**
Implement this exact primary flow:

`MAIN DASHBOARD`

→ Admin clicks `START ROUND`

→ `ROUND TITLE SLIDE`

→ Admin clicks `NEXT`

→ `ROUND BLOCK 1`

→ Admin clicks `NEXT`

→ `ROUND BLOCK 2`

→ etc.

The system must never automatically cycle through round blocks.

The Admin controls each transition.

---

## 7. Temporarily show dashboard without losing round position

**User Story — Admin**
As an Admin, I want to temporarily switch from the current round content back to the exchange dashboard and then return to exactly where I was, so that I can show standings without losing my place in the round.

**Technical Story**
Separate:

* the **underlying active round presentation position**
* the **currently displayed Big Screen mode**

For example:

```text
active_round_id = 4
active_round_step = 6
screen_mode = DASHBOARD
```

The round remains at part 6 even though the dashboard is temporarily shown.

When the Admin switches back, the system restores:

* round 4
* part 6

Do not reset the active block or recompute position.

---

## 8. Dashboard button becomes “Show Previous Screen”

**User Story — Admin**
As an Admin, I want the dashboard toggle to intelligently change into a return button after I temporarily show the dashboard, so that returning to the exact previous screen takes one click.

**Technical Story**
When the Admin is presenting round/prediction/roulette content, show:

`SHOW MAIN DASHBOARD`

When pressed:

* store the current presentation as `previous_screen`
* change visible Big Screen mode to `DASHBOARD`

The same button then becomes:

`SHOW PREVIOUS SCREEN`

When pressed:

* restore the saved previous presentation exactly
* including round ID
* block/part index
* prediction ID if relevant
* roulette state if relevant
* change button back to `SHOW MAIN DASHBOARD`

This should behave like a presentation stack with one temporary dashboard overlay, not like navigating away from the round.

Example:

`Round 4 / Part 6`

→ `SHOW MAIN DASHBOARD`

→ Dashboard

→ `SHOW PREVIOUS SCREEN`

→ `Round 4 / Part 6`

---

## 9. Preserve round state while dashboard is shown

**User Story — Admin**
As an Admin, I want timers, active markets, and the current round to continue behaving correctly while I temporarily show the dashboard, so that changing what the audience sees does not alter game logic.

**Technical Story**
Big Screen presentation mode must be separate from game/business state.

Switching to the dashboard must **not**:

* pause the round
* stop prediction timers
* resolve anything
* change active round
* change current round block
* close roulette
* alter wallets

It only changes what is rendered on `/screen/:gameId`.

# PREDICTION BIG SCREEN

## 10. Prediction question replaces “PREDICTION OPEN”

**User Story — Audience**
As someone looking at a prediction on the Big Screen, I want the actual prediction question to be the dominant text, so that everyone immediately knows what they are betting on.

**Technical Story**
Update the Big Screen prediction presentation.

Where the design currently uses a large centered label such as:

`PREDICTION OPEN`

replace that main headline with the actual prediction question.

For example:

Instead of:

`PREDICTION OPEN`

show:

`WILL TWAN FINISH THE CHALLENGE IN UNDER 30 SECONDS?`

The prediction question should:

* be large
* centered
* use the dominant typography defined by the design handbook
* wrap safely for longer questions

A smaller status indicator can still show:

`MARKET OPEN`

or:

`BETTING OPEN`

elsewhere in the layout.

Do not make generic state text visually more important than the market question.

# ROULETTE SETTINGS

## 11. Configurable roulette spin duration

**User Story — Admin**
As an Admin, I want to configure how long the roulette wheel spins before stopping, so that I can control the pacing and suspense of roulette.

**Technical Story**
Add a setting to:

`/admin/:gameId/settings`

Recommended field:

`Roulette spin duration (seconds)`

Persist per game, for example:

`roulette_spin_duration_seconds`

Set sensible validation bounds. For example:

* minimum: 2 seconds
* maximum: 30 seconds

When Admin initiates a roulette spin:

* server determines/records the winning result
* server records the spin start time and configured duration
* clients animate for that duration
* result becomes visually final when that duration expires

The configured duration affects animation timing only. It must not change or randomly determine the result on the client.

---

## 12. Synchronize roulette animation across screens

**User Story — Admin / Audience**
As users watching roulette on different screens, we want the roulette spin to appear synchronized, so that the Admin preview and main Big Screen do not finish at different times.

**Technical Story**
Persist something similar to:

* `spin_started_at`
* `spin_duration_ms`
* `winning_number`

Clients derive animation progress from server timestamps.

Do not start an independent arbitrary timer whenever each client receives the state, because polling latency could make the screens visibly out of sync.

# ROUND GROUPS

## 13. A player may only belong to one group within the same round

**User Story — Admin**
As an Admin creating groups for a round, I want players who already belong to one group to be unavailable for selection in another group, so that I cannot accidentally assign the same person to multiple teams.

**Technical Story**
In the round-group editor, determine all group memberships for the current round.

For each group:

* current members remain selectable/removable in that group
* players belonging to another group in the same round appear disabled or are omitted from the available-player selector

The UI should make the reason clear, for example:

`Daan — already in Team A`

Do not rely only on disabled checkboxes.

---

## 14. Enforce one-group-per-round on the backend

**User Story — Admin**
As an Admin, I want the system to prevent invalid duplicate group memberships even if two actions happen quickly or the UI is stale.

**Technical Story**
Enforce the one-group-per-round rule server-side/database-side.

A player may:

* belong to Group A in Round 1
* belong to Group B in Round 2

But may not:

* belong to Group A and Group B in Round 1 simultaneously

Structure the schema or transactional validation accordingly.

Do not rely solely on frontend checkbox state.

When moving a Player between groups, either:

* explicitly remove then add, or
* expose a safe `MOVE PLAYER` operation.

# ADMIN CONTROL PANEL PRIORITY ACTIONS

## 15. Turn Control Panel into the host’s operational cockpit

**User Story — Admin**
As the person actually hosting Market Mayhem, I want the actions I use repeatedly during the evening directly available on the Control Panel, so that I rarely need to leave that page while the game is running.

**Technical Story**
Treat `/admin/:gameId` as the live operations surface.

Configuration tasks stay on dedicated pages. Repeated live-event actions should be surfaced on the Control Panel.

Based on the current game flow, prioritize the following actions.

---

## 16. Priority action: Start / complete round

**User Story — Admin**
As an Admin, I want to start and complete rounds directly from the Control Panel because these are core hosting actions.

**Technical Story**
Expose:

* `START ROUND`
* `COMPLETE ROUND`

in the current-round component.

When no round is active:

* show upcoming rounds with Start.

When one is active:

* show current round
* show Complete action

Use existing round backend actions.

---

## 17. Priority action: Previous / Next content

**User Story — Admin**
As an Admin, I want Previous and Next to be among the most prominent controls, because I use them throughout every round.

**Technical Story**
Place `PREVIOUS` and `NEXT` immediately adjacent to or below the Live Big Screen Preview.

These should be primary operational buttons rather than buried controls.

Disable appropriately:

* Previous on first possible step if no earlier step exists.
* Next when there is no next round block unless completing the round is the intended next action.

---

## 18. Priority action: Dashboard / Previous Screen toggle

**User Story — Admin**
As an Admin, I want the dashboard toggle constantly accessible, because I may want to briefly show standings at any moment.

**Technical Story**
Place:

`SHOW MAIN DASHBOARD`

or its temporary replacement:

`SHOW PREVIOUS SCREEN`

next to the primary presentation controls.

Do not hide this inside Settings or a dropdown.

---

## 19. Priority action: Active prediction controls

**User Story — Admin**
As an Admin, I want currently relevant prediction controls visible on the Control Panel, so that I do not need to navigate to the Predictions page during live play.

**Technical Story**
Show only predictions relevant to the current/active context.

For each relevant prediction, expose high-frequency actions such as:

* `SHOW PREDICTION`
* resolve YES
* resolve NO
* cancel when permitted

Also show:

* question
* status
* countdown/closed state
* amount/number of bets

Creation/editing remains on the Predictions page.

---

## 20. Priority action: Roulette controls

**User Story — Admin**
As an Admin, I want roulette controls directly on the Control Panel whenever roulette is the active round block, so that I can run it without changing pages.

**Technical Story**
Conditionally show roulette controls when the active block is roulette:

* OPEN BETTING
* CLOSE BETTING
* SPIN

And the current:

* roulette state
* number of bets
* total stake
* latest result

Do not permanently consume Control Panel space with roulette controls when roulette is not relevant.

---

## 21. Priority action: Quick coin adjustment

**User Story — Admin**
As an Admin, I want quick coin corrections accessible during live play, but I do not want that utility to dominate the Control Panel.

**Technical Story**
Keep the compact Quick Coin Adjustment directly beneath the Live Big Screen Preview as already specified.

Fields remain:

* Player
* signed amount
* mandatory reason
* optional round
* Save

This should be visually secondary to round/presentation controls.

---

## 22. Priority action: Active group scoring

**User Story — Admin**
As an Admin running a group-based round, I want quick group scoring on the Control Panel, so that I can award or deduct coins from an entire team without opening the Round editor.

**Technical Story**
If the current active round contains groups, show a compact `GROUP SCORING` component on the Control Panel.

Provide:

* group selector
* signed coin amount
* reason
* Save

Reuse the existing group adjustment backend logic.

Hide this component entirely if the active round has no groups.

---

## 23. Priority action: Live Duolingo question controls

**User Story — Admin**
As an Admin running a live multiple-choice question, I want its relevant controls on the Control Panel, so that opening, closing, and revealing the answer can happen while I watch the Big Screen preview.

**Technical Story**
When the current round block is a `DUOLINGO_QUESTION`, show contextual controls:

* OPEN QUESTION
* CLOSE ANSWERS
* REVEAL ANSWER
* settlement/result status

Also show:

* responses received / eligible players

Do not show these controls for unrelated block types.

# CONTROL PANEL LAYOUT PRIORITY

## 24. Organize Control Panel by frequency of use

**User Story — Admin**
As an Admin, I want the Control Panel layout to prioritize what I need right now rather than presenting every possible feature equally.

**Technical Story**
Structure the page roughly in this priority:

**Primary**

* Live Big Screen Preview
* current round / current part
* Previous
* Next
* Start/Complete Round
* Show Dashboard / Show Previous Screen

**Contextual**

* active prediction controls
* roulette controls
* Duolingo controls
* group scoring

Only show these when relevant.

**Secondary**

* Quick Coin Adjustment
* recent ledger activity
* high-level status information

**Configuration**
Do not put configuration-heavy forms here:

* create prediction
* create round
* edit player
* game Settings
* edit round blocks

Those remain on dedicated Admin pages.

This lets the Control Panel become the host's **live control desk**, rather than a second copy of every Admin screen.
